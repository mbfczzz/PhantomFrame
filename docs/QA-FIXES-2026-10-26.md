## 上游日志

此前进行中的上游日志功能一并保留：管理员入口 `/admin/upstream`，用户任务详情可查看自己的调用信息。独立日志保留渠道、模型、用户、阶段、上游任务 ID、HTTP 状态、耗时和退款情况，敏感参数脱敏。用户隐藏生成记录后，管理员仍能查看调用与原任务。

两个本地模拟渠道验证成功提交/轮询/下载和 HTTP 401 失败，合计 4 次 localhost HTTP 请求；没有真实供应商请求。浏览器检查渠道筛选、任务 ID 复制、参数脱敏、嵌套任务详情及移动端显示。

## 升级兼容性

启动会自动创建操作回执、管理员锁和上游日志表，并为已有 `jobs` 表添加隐藏、请求摘要及退款重试字段；旧库迁移和重复迁移均有回归覆盖。

自定义客户端需要遵循两项接口变化：转账/管理员调账必须提供稳定 `Idempotency-Key`；生成轮询应继续等待 `refund_pending`，直到 `failed` 且 `refunded=true`。网页端已同步修改。只在本机 Nginx 代理的现有部署可直接使用默认可信代理配置；额外代理应明确配置地址范围。

升级前已经物理删除的任务无法凭空恢复；本次保护升级后的删除操作。已失败但退款尚未完成的旧 `running` 任务会在启动恢复阶段处理。账户余额仍以原人民币分单位保存，没有更改历史金额。

本轮修复现有兑换码、转账、调账和生成扣退款流程。项目仍未实现真实支付订单、网关验签、支付回调与自动对账，因此没有把真实付款闭环列为已验收能力。上述结果是本地隔离验证，不代表已经部署或执行了生产压测。

## 二次复查追加

按“再仔细检查”的要求，增加失败注入和真实双标签页时序测试，复现并修复了以下 5 类边界问题。原始失败日志为 `test-results/recheck-before.log` 和 `test-results/recheck-ui-before.log`，不是仅凭静态推测判断。

| 问题 | 修复与验证 |
|---|---|
| 延迟退款已到账，错误信息仍写“退款处理中” | 退款事务提交终态时统一更新文案；验证状态、退款标记和提示一致 |
| 失败输出删不掉后丢失重试机会；手动删除素材也可能提前抹掉记录 | 新增持久化 `job_cleanups` 队列，独立扫描、延迟重试，并在升级时补入旧失败任务的残留文件；清理失败保留素材记录。文件清理与资金补偿分开调度，存储故障不会阻塞后续退款。手动删除失败返回错误并保留重试目标 |
| 生成请求已通过鉴权、等待数据库锁期间账号被停用，仍可能扣款 | 在生成事务锁内复核账号状态与会话版本；验证旧请求被拒绝且任务、扣费流水均为 0 |
| 编码密钥、嵌入文本的签名 URL、Cookie/私钥字段，以及上游任务 ID 反射凭据未被完整屏蔽 | 扩展脱敏字段与 URL/编码处理；日志读取使用已脱敏的任务 ID，真实轮询仍保留原始 ID。验证写入、状态同步和历史补录三条路径，管理员与普通用户视图都不会回显测试凭据 |
| 旧标签页的迟到回执清除了新操作的待确认记录 | 清除时核对操作编号，进行中请求按操作编号隔离，使用浏览器锁协调跨标签页保存/提交。真实双标签页验证：旧回执不会抹掉新记录；并发提交同一待处理转账只有一次 POST 和一次扣款 |

新增可重复运行的测试：[recheck_test.go](../internal/api/recheck_test.go)、[test-recheck-ui.mjs](../scripts/test-recheck-ui.mjs)，浏览器命令为 `npm run test:recheck-ui`。构建、后端完整回归、9 项既有故障场景和多渠道日志专项均继续验证；本次不重复渲染没有视觉变更的 132 组页面矩阵。
