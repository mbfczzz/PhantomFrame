## P1 详细复现

### F01 · Nginx 后所有用户共享限流桶

位置：[http.go:208](../internal/api/http.go)、[Nginx 代理配置](../deploy/nginx/phantomframe.tcmzhan.com.conf)。

`limit()` 直接使用 `r.RemoteAddr`，没有处理受信代理传入的真实地址。当前部署中 Nginx 连接 `127.0.0.1:3001`，Go 看到的 TCP 来源都为本机回环地址，设置了 `X-Real-IP` 和 `X-Forwarded-For` 也没有生效。

复现：在同一个本地 TCP 来源下，第一组请求携带客户端 A 的转发地址，连续执行 31 次错误登录；再携带完全不同的客户端 B 地址，用正确账号登录。A 前 30 次返回 401，第 31 次返回 429；B 的正确登录也返回 **429**。

当前同类实现还用于注册、兑换和生成接口，因此影响不只是一位用户的登录体验。建议先限定可信代理，再使用可信链中的实际客户端地址，必要时结合用户 ID 分桶；不要简单信任任意请求提供的第一个转发地址。

证据：[B01 原始结果](../test-results/audit/api-findings.json)。

### F02 · 删除生成记录破坏消费统计、调用审计和幂等

位置：[generation.go:404](../internal/api/generation.go)、[generation.go:222](../internal/api/generation.go)、[account.go:17](../internal/api/account.go)、[任务详情删除入口](../src/pages/Creation.tsx)。

`DELETE /api/jobs/{id}` 直接删除 `jobs` 行；`/usage` 从这些行统计消费，生成幂等也只查询这些行。后台全站调用同样依赖此表。

复现：用 API Key 和固定幂等键提交本地 demo，完成一次 ¥1 任务，删除它，再重发完全相同的请求和幂等键。

| 阶段 | 测试余额 | API 已消费统计 | 结果 |
|---|---:|---:|---|
| 第一次生成完成 | ¥999 | ¥1 | 正常扣费 |
| 删除记录 | ¥999 | **¥0** | 账本扣费仍在，后台任务详情返回 404 |
| 相同幂等键重发 | **¥998** | 新任务重新计入 | 创建不同任务 ID，再扣 ¥1 |

账本最终存在两条扣费，共 ¥2。删除展示记录不应同时移除财务事实与请求去重依据。

建议用户删除使用隐藏/软删除；保留不可被展示删除抹掉的调用事实和幂等记录；累计消费以不可变账本或独立计量事实为依据。

证据：[B02 原始结果](../test-results/audit/api-findings.json)。

### F03 · 转账成功但回执丢失后，页面重试再次划款

位置：[account.go:81](../internal/api/account.go)、[账户转账表单](../src/pages/Account.tsx)。

转账接口没有操作幂等记录，表单请求也没有稳定的业务操作 ID。页面只在成功收到响应后刷新余额。

浏览器复现：打开真实转账窗口，填写 ¥5；通过 Playwright 先让后台完成请求，再中断返回给浏览器的响应。页面提示网络失败，窗口仍可再次提交。用户重试后又完成了一次划款。

| 阶段 | 测试主账户余额 |
|---|---:|
| 提交前 | ¥975 |
| 后台已成功，前端回执丢失 | ¥970 |
| 用户重试 | **¥965** |

两次后台请求都成功，用户一次 ¥5 意图实际转出 ¥10。另用相同 `Idempotency-Key` 重放接口也得到两次成功；此接口目前不会处理该键。

建议为资金操作生成稳定操作 ID，并在同一数据库事务内记录幂等结果与双边流水。超时后按操作 ID 查询结果，并刷新实际余额，避免把“不知道是否成功”等同于“未发生”。

证据：[U01 浏览器结果](../test-results/audit/browser/faults/results.json)、[回执丢失时的窗口](../test-results/audit/browser/faults/transfer-response-lost.png)。B03 与 U01 是同一问题，不重复计数。

### F04 · 退款 SQL 失败后任务长时间挂起

位置：[worker.go:130](../internal/api/worker.go)、[worker.go:158](../internal/api/worker.go)、[退款事务](../internal/api/generation.go)。

专项测试让本地 HTTP 模拟上游返回 500，再通过测试库触发器模拟退款流水写入失败。系统输出 `job recovery deferred`；移除故障后，任务仍为 `running`、`refunded=false`，余额保持扣费状态，退款流水为 0。

已继续观察超过 **695 秒**，问题仍存在。正常持有调度租约时，消费者只领取 `queued`，没有再次处理这个退款失败的 `running` 任务；重启/换主时才有一次批量回收机会。退款失败不能只留下日志。

建议引入可持久化的退款待处理状态或补偿队列、重试时间与次数；独立扫描并重试补偿，继续保持退款唯一性和事务原子性。测试故障已移除，没有把故障触发器留在运行环境中。

证据：[B04 原始结果和后续观察](../test-results/audit/api-findings.json)。该任务是本地模拟，不是真实付费模型。

### F05 · 并发管理员降级导致后台与重启恢复同时失效

位置：[admin.go:393](../internal/api/admin.go)、[db.go:364](../internal/api/db.go)。

接口只禁止“降级/停用当前管理员自己”。当管理员 A 降级 B、B 同时降级 A 时，两次请求均可在权限校验后提交，最后没有管理员。

专项测试使用数据库锁同步两个已鉴权请求：两个 PATCH 均返回 200，活跃管理员数量变为 **0**。随后启动另一测试进程：初始化逻辑尝试创建同名 `audit-admin`，撞到已有账号的用户名唯一索引，进程以 `Error 1062 / Duplicate entry` 崩溃。

此问题要求已有至少两个管理员，不是普通用户提权。建议使用所有管理员状态变更共同竞争的锁/事务约束，保证至少一名有效管理员；初始化恢复逻辑也须处理默认用户名已存在的情况，避免重启循环失败。

证据：[B05 原始结果](../test-results/audit/api-findings.json)、[重启崩溃日志](../test-results/audit/admin-restart-failure.log)。测试完成后已恢复测试账号角色。

### F06 · 浅色主题的选中态与徽章文字对比度不足

位置：[palette.css:67](../src/palette.css)、[徽章及 Tabs 样式](../src/styles.css)、[主题组件样式](../src/cinematic.css)。

42 次扫描中，12 个浅色路由命中同一类问题。示例：

| 元素 | 前景 / 背景 | 实测对比度 |
|---|---|---:|
| 模型分类选中项、文档代码文字 | `#16803e` / `#e2ece7` | **4.14:1** |
| 选中 Tabs、后台入口文字 | `#16803e` / `#e5eeea` | **4.23:1** |
| 正常/管理员徽章 | `#15803d` / `#e4ede9` | **4.20:1** |

这些是 12–13px 的正常字号文字，不属于品牌标识或纯装饰例外；[WCAG 2.2 SC 1.4.3](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html) 要求此类文本至少 4.5:1。建议统一调整浅色主题的文字与柔和背景令牌，而不是逐页覆盖颜色。

证据：[完整对比度节点](../test-results/audit/browser/violations.json)、[浅色手机后台截图](../test-results/audit/browser/admin-models-light-390.png)。29 个重复 DOM 命中按一个主题根因计数。

## P2 详细复现

### F07 · 工单重开绕过未结束数量上限

位置：[tickets.go:93](../internal/api/tickets.go)、[tickets.go:129](../internal/api/tickets.go)。

创建接口会限制最多 50 个 `open/replied` 工单，重新打开接口没有同样约束。

测试预置 49 个有效工单夹具：创建第 50 个返回 201；继续创建返回 429；关闭一个后创建替代工单返回 201；再重开原工单返回 **200**，未结束总数变为 **51**。

建议创建与重开共用同一限制，并在相同用户锁下检查。证据：[B06](../test-results/audit/api-findings.json)。

### F08 · 删除末页最后一条素材后，剩余数据无法从当前分页进入

位置：[Creation.tsx:1037](../src/pages/Creation.tsx)、[Creation.tsx:1130](../src/pages/Creation.tsx)、[lib.tsx:708](../src/lib.tsx)。

普通测试账号上传 25 个本地 PNG，进入第二页删除唯一素材。页面保持 `page=2`，总数降到 24 后公共分页组件直接隐藏，画面显示“资产库还是空的”。实际接口仍有 **24 条素材**，但当前页面没有上一页按钮。

建议删除后依据新总数校正当前页，或在当前页超过页数时自动退一页；同一公共分页用法也应复查。证据：[U04](../test-results/audit/browser/faults/results.json)、[误显示空库截图](../test-results/audit/browser/faults/assets-pagination-stranded.png)。

### F09 · 退出登录服务失败没有界面反馈

位置：[Shell.tsx:88](../src/components/Shell.tsx)。

把退出接口响应模拟为 503 后点击退出：页面停留原位置，出现未处理的 `AUDIT logout unavailable` 异常，没有错误提示。`logout()` 直接等待 POST，没有捕获失败。

建议捕获失败并提供明确反馈与重试，同时定义会话撤销失败时的本地退出策略。证据：[U02](../test-results/audit/browser/faults/results.json)。

### F10 · `/me` 的 503 被误判成需要重新登录

位置：[Shell.tsx:130](../src/components/Shell.tsx)。

测试账号已正常登录。只把首次 `/api/me` 的响应模拟为 503，再进入资金流水页，最终落到 `/login`，没有显示服务暂不可用。判断分支把“没有拿到用户数据”和 401 混在一起。

建议只有确定的未鉴权状态跳转登录；503、网络错误、超时分别提供服务异常和重试状态，避免误导用户重新输入密码。证据：[U03](../test-results/audit/browser/faults/results.json)、[错误登录页截图](../test-results/audit/browser/faults/session-service-503.png)。

### F11 · 手机登录/注册页的页脚撑宽页面

位置：[cinematic.css:1507](../src/cinematic.css)、[cinematic.css:3104](../src/cinematic.css)。

基础页脚宽度 1120px，手机样式把最大宽度改成 430px，却没有限制到父容器实际宽度。

- 390px 视口：页脚宽 **430px**，边界 `left=-20 / right=410`，文档宽 **410px**。登录、注册在深浅主题都可复现。
- 320px 补查：页脚仍宽 **430px**，文档宽 **375px**。

这是项目“页面无横向溢出”验收条件的明确失败；此处没有仅凭空白溢出就断言整页违反 WCAG Reflow。建议移动端将页脚宽度约束到父容器，并复测 320/390px。

证据：[DOM 边界测量](../test-results/audit/browser/verified-ui-details.json)、[手机登录页](../test-results/audit/browser/login-dark-390.png)。

### F12 · Tabs 标记与键盘交互不匹配

位置：[lib.tsx:648](../src/lib.tsx)。

公共 Tabs 使用 `tablist/tab` 语义，但没有方向键处理或 roving tabindex。账户页聚焦“兑换充值”后按右方向键，焦点仍停在原标签；全部 4 个标签的 `tabIndex` 都是 0，`aria-controls` 均为空，找不到 `tabpanel`。

这与 [WAI-ARIA APG Tabs](https://www.w3.org/WAI/ARIA/apg/patterns/tabs/) 的键盘与面板关联模式不符。建议补齐左右键导航、活动标签焦点管理及面板关联。这里按组件语义/键盘规范问题列为 P2，没有把 APG 的全部建议直接当作 WCAG 强制条款。

证据：[键盘测量](../test-results/audit/browser/verified-ui-details.json)。

## 付款与充值的能力边界

当前系统没有支付订单、支付渠道签名校验、支付成功回调或自动支付对账实现。已经实现且经过测试的是：

1. 管理员创建有金额、有效期的兑换码；
2. 用户兑换时锁定兑换码并在同一事务中写余额、流水及使用状态；
3. 管理员人工调账并记录审计；
4. 配置 `purchaseUrl` 后展示外部购买入口。

这与 [README 的现有说明](../README.md) 一致，因此**不把未实现的网关回调伪报为代码漏洞**，也不宣称“付款闭环已经验收通过”。如业务希望实现在线付款后自动到账，还需要独立验收订单、验签、重复通知、金额/币种校验、退款和对账等流程。本轮未点击或请求真实付款接口。

1. 可信代理与限流分桶；保留调用/幂等事实；资金操作幂等；持久化退款补偿；最后管理员的并发约束及恢复。

4. F11：`$impeccable adapt`，校正认证页手机布局。
5. 完成上述修复后再执行 `$impeccable polish`；复用本轮复现步骤验收，不只重复正常流程。
