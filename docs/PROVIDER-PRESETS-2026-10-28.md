# 全部供应商启动预设（2026-10-28）

本次纠正此前只自动准备 OpenCrow 的范围遗漏：将用户原清单中的 **34 家供应商、249 条非 3D 路由**全部作为非敏感预设随应用提供，连同 OpenCrow 共 **35 家供应商**。

## 用户可见变化

- 启动后「渠道管理」出现全部供应商，无需先导入 CSV。
- 「新增渠道 → 接入协议」能选择全部 34 家清单供应商。选中后显示已预置的渠道名称与路由数量，可直接进入该供应商的路由页填写 Key。
- 渠道卡片的「配置路由与 API Key」按供应商过滤，避免在全部 249 条中寻找。
- 路由的已知地址、模型映射、原有启用标记与参数已准备好；Key 留空并独立保存。
- 已有完整配置或导入数据保持原值，包括密钥、价格、参数、渠道名称、停用状态和余额。
- 新增预设模型默认停用。创建时沿用无歧义且兼容的同名价格，其他保留待定；填 Key 不会自动启用未审核模型。

原清单 **6 条路由缺少地址**，会标注「待补地址」，搜索该状态可以找到全部 6 条。不会把其他路由的地址或凭据自动套用给它们。

## 实现边界

`internal/api/provider_presets.json` 只包含经过字段筛选的非敏感元数据，没有 API Key，也没有伪造测试 Key。启动仅补齐缺失的路由和模型，不调用上游，不生成任务、不扣费。原始含 Key 的 CSV 仍被 Git 和 Docker 构建上下文忽略，需要时由管理员显式导入。

启动预置与显式导入使用同一事务互斥锁；同一供应商下不同地址、不同密钥的路由保持独立。重复启动及并发启动不会重复创建或覆盖已存在的配置。

## 第二轮边界复查

本轮补充检查启动修复、并发导入、标识冲突、地址变更和供应商页面切换，发现并修复以下四类问题。

| 问题 | 触发条件与影响 | 修复行为 |
| --- | --- | --- |
| 已有路由缺少关联模型时未修复 | 数据恢复或旧数据不完整时，启动只检查路由是否存在，路由一直没有可配置的模型 | 根据数据库中已审核的路由映射补建停用模型；不覆盖路由地址、密钥和原有配置，不重新创建已有绑定 |
| CSV 导入未检查供应商／模型 ID 归属 | 生成的 ID 被其他配置占用时，导入可能误改原模型的供应商和上游绑定，或使用错误协议的渠道 | 在写入前检查协议及模型路由归属；冲突时整笔事务回滚，保留原模型、渠道和路由 |
| 更换地址没有要求重新审核模型 | 编辑已启用路由的地址后，模型仍可继续使用新地址调用；清空地址也保留了启用标记 | 更换或清空地址时停用关联模型，保留价格；只轮换 Key 或规范化末尾斜杠不影响原启用状态；界面说明重新启用要求 |
| 切换供应商保留旧筛选状态 | 在供应商页搜索后返回“全部供应商”，旧搜索条件仍生效，可能误以为路由缺失 | 按供应商范围重建页面状态，清理旧搜索、页码及未保存的编辑状态；覆盖前进／后退导航 |

后端前三类问题均先通过新增用例观察到失败，再验证修复通过。浏览器测试补充等待导航后的页面渲染完成，避免只等待 URL 更新就读取旧界面。
