# API 性能与回归检查（2026-10-29）

## 测试范围

同一台 Windows / Intel i5-14400 电脑，本机隔离 MySQL 3307、Redis 6380，20 个供应商实例、1000 个文本模型、2000 条价格规则、初始 1000 条渠道目录记录。HTTP 请求走本机回环，使用真实登录会话，耗时包含鉴权、数据库访问、JSON 编码和读取完整响应，不含登录本身的密码校验。

模型目录接口返回 1000 条记录，并固定等待 50ms；首次同步新增 950 条，重复同步不覆盖已有条目。实际供应商、真实模型、支付和生产数据均未访问。

大多数接口每轮测 12 个请求；任务入队串行 8 个、4 并发模型列表 20 个、4 并发入队 12 个、重复同步 5 个。优化前测一轮，优化后测两轮，下表保留两轮区间，不挑最好值。P50/P95 使用最近观测值分位数；这些小样本用于定位开销，不是生产 SLA。

## 实际修改

1. 模型列表改成批量读取供应商、价格及兼容路由元数据。1000 个模型的一次 HTTP 请求从 **2002 次 SQL 降为 4 次**，返回的模型数量、价格精度、版本标记和响应体大小保持一致；此次完整列表约 1,022,002 字节。
2. 渠道目录按页批量查询已发布模型。20 条目录的请求从 **24 次 SQL 降为 5 次**，查询仍按供应商实例限定，其他账号的模型和密钥不会混入。
3. 同步目录改成分批检查已有 ID、每批插入最多 100 条。整个同步仍使用一个事务，任何一批失败都会回滚；人工修改的名称、参数、协议选项和独立 Key 不被覆盖。
4. 增加 `(provider_id, upstream_model)` 联合索引，固定协议元数据在进程内只构建一次。供应商账号配置、密钥、模型售价和余额没有放入此静态缓存。

批量读取的 SQL 参数按最多 1000 个 ID 分块，避免把目录增长转化为单条 SQL 参数上限问题。

## 排队与模型生成

另外执行了 6 个模拟文本任务，每次上游响应固定等待 100ms。现有调度器同时处理 **2 个任务**：

- 第一条开始请求模拟上游：约 27ms。
- 最后一条开始请求模拟上游：约 280–306ms。
- 最后完成：约 411–442ms。
- 两轮分别恰好请求 6 次模拟生成接口，余额扣款恰好对应 6 次，之前的入队／撤销探针全部退回。

任务提交成功只代表入队，不能等同于模型生成完成。真实供应商生成时长、网络、生产数据库及长视频任务的排队速度不在上述本机数字内。本轮没有调整后台任务并发数量。

## 功能验证与复现

新增回归覆盖批量列表与原单条格式的一致性、价格版本与精度、兼容路由的输出限制、重复输入不污染价格、不同实例的目录隔离、第二批写入失败时第一批回滚，以及重复拉取保留人工配置。

全量后端 **105 个顶层测试、1005 个 PASS 节点通过，0 跳过**；原有 **41 条浏览器流程**和新实例 **6 条流程**通过。构建、`go vet ./...` 和凭据扫描通过。真实付费模型调用 0，真实支付调用 0。

在已配置隔离数据库环境及 `PF_INTEGRATION=1` 后运行：

```powershell
go test ./internal/api -run '^$' -bench '^BenchmarkProviderAPI$' -benchtime=1x -count=1
```

可用 `PF_PERFORMANCE_REPORT` 指定 JSON 输出路径。通用 benchmark 的 `ns/op` 行不用于本表；本表取自 JSON 中逐个 HTTP 请求的耗时。
